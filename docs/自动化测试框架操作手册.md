# API + Web + App 自动化测试框架操作手册

# Web Trace 使用指南

在项目根目录，使用已安装依赖的 Python 环境运行：

```powershell
python scripts/automation.py test --type web --env uat --tracing retain-on-failure
python scripts/automation.py test --type web --env uat --headed --tracing on
```

`retain-on-failure` 只保留 setup/call/teardown 任一阶段失败的 Trace；
`on` 保留全部；`off` 关闭。命令行优先于 YAML 的 `web.trace`。
不传参数且 YAML 开关为 false 时不录制。

默认文件位于 `reports/web-evidence/<运行ID>/<用例>/<尝试ID>/trace*.zip`。
直接 pytest 的 `--output` 作为运行目录的父目录，其下仍自动创建运行 ID。
每个 worker/运行/重试独立存储，不复用或清空历史运行目录。
插件创建的多个 Context 会分别附加 Trace。

Allure 用例附件中下载 `Playwright trace.zip`（或带序号的文件），打开：

```powershell
python -m playwright show-trace "下载或生成的trace.zip绝对路径"
```

先查看失败动作和前后 DOM 快照，再看对应 Network 请求、响应和 Console。
ZIP 是可下载附件，Allure 不直接提供交互式 Trace Viewer。
失败截图和安全上下文附件继续保留。

GitHub Actions 的 web-traces 工件保留 7 天；Jenkins 归档原始 ZIP，
保存期限遵循该 Jenkins 作业的构建保留策略。Allure 附件还有一份副本。
本地历史文件不自动删除，需要按实际存储需求清理旧运行。

只覆盖 pytest-playwright 的 page/context/new_context fixture 管理的上下文。
手工 WebBrowser/browser.new_context 不自动录制；进程强杀、浏览器崩溃、
上下文创建前失败可能没有可用 Trace。Trace 展示现场，不代替业务断言。

Trace 包含页面、网络及源码，现有 JSON 脱敏不覆盖 Trace。
包含 Trace 的 Allure 报告和 CI 工件应限制访问，发布报告时注意附件同样会被发布。

这是一份从安装到落地的完整手册。你同时负责 API、Web、App 自动化时，只需要维护这一套框架、一个 `requirements.txt` 和这一份手册。

## 1. 先理解框架怎么分工

三端使用同一种语言和测试入口，但不要把同一个业务场景重复写三遍。

```text
API 用例  -> api/     -> HttpClient -> 后端接口
Web 用例  -> pages/   -> Playwright -> 浏览器
App 用例  -> screens/ -> Appium     -> 真机/模拟器
                         |
                         +-> pytest / fixture / Allure / 配置 / 数据清理共用
```

推荐用例比例：

| 类型 | 建议占比 | 主要覆盖 |
|---|---:|---|
| API | 60%～70% | 参数、权限、边界、异常、业务状态和数据一致性 |
| Web | 15%～20% | 浏览器核心用户链路和前端交互 |
| App | 10%～15% | 移动端核心链路、系统权限和设备交互 |
| 跨系统 E2E | 少量 | 最关键的完整业务闭环 |

原则：业务分支主要交给 API；Web 和 App 少而精，只验证用户真正使用的核心链路。

## 2. 软件与版本要求

### 2.1 所有人都要安装

- Git
- Python 3.10、3.11 或 3.12
- VS Code 或 PyCharm
- Allure 命令行（需要查看图形报告时安装）

验证：

```powershell
git --version
python --version
python -m pip --version
```

### 2.2 Web 额外要求

Playwright 浏览器由命令安装，不需要提前安装 Chrome：

```powershell
python -m playwright install chromium
```

需要 Firefox 或 WebKit 时：

```powershell
python -m playwright install firefox webkit
```

### 2.3 Android App 额外要求

- Windows 10/11，BIOS 已开启 CPU 虚拟化。
- Node.js 20.19+、22.12+ 或 24+，npm 10+。
- JDK 17 或更高版本；本框架安装脚本使用 JDK 21 LTS。
- Android SDK、Android Emulator 和 API 34 系统镜像。
- Appium Server、UiAutomator2 Driver。
- Appium Inspector（编写定位器时再安装，不是执行用例的必需项）。

项目提供一条推荐安装路径，不需要同时安装多套工具。先安装 Node.js LTS，
然后在项目根目录打开 PowerShell：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\setup_android_emulator.ps1
```

脚本安装到当前用户目录，不删除已有 SDK、JDK、AVD，也不会覆盖已有 `.env`。
SDK 安装器可能更新所选组件；脚本不再永久修改用户级 `JAVA_HOME`、`ANDROID_HOME` 和 PATH。
已存在的不同 Appium/UiAutomator2 版本会阻断，避免静默覆盖。
它会自动完成：

1. 下载并校验 Microsoft OpenJDK 21。
2. 下载并校验 Android 命令行工具。
3. 安装 `platform-tools`、`emulator`、Android 34 平台和 x86_64 系统镜像。
4. 创建 `Pixel_6_API_34` 模拟器并检查 WHPX 硬件加速。
5. 安装 Appium 3.4.2、UiAutomator2 8.5.2。
6. 下载并校验官方 ApiDemos 示例 APK。
7. 在不存在 `.env` 时生成可直接冒烟的本地配置。

当前已验证组合（2026-09-04）：

| 组件 | 版本 |
|---|---|
| Microsoft OpenJDK | 21.0.12.1 LTS |
| Android SDK Command-line Tools | 22.0 |
| Android Platform / 系统镜像 | API 34 / Android 14 |
| Android Emulator | 37.1.11 |
| Android Platform Tools | 37.0.1 |
| Appium Server | 3.4.2 |
| UiAutomator2 Driver | 8.5.2 |

安装完成后，在项目终端先启用进程级工具链再验证；每个新终端都需要执行第一行：

```powershell
. .\scripts\use_android_env.ps1
java -version
adb version
emulator -list-avds
emulator -accel-check
appium --version

python scripts/automation.py doctor --env uat --type app
```

`emulator -accel-check` 应显示 WHPX 可用。真机执行时，`adb devices` 必须出现状态为
`device` 的设备；`unauthorized` 表示手机尚未允许 USB 调试。

#### 安装回滚边界

安装内容相互独立，项目代码回滚不会自动删除本机工具：

```powershell
# 只移除 Appium 驱动和 Server
appium driver uninstall uiautomator2
npm uninstall -g appium

# 只删除本框架创建的模拟器（执行前先用 emulator -list-avds 核对名称）
avdmanager delete avd --name Pixel_6_API_34
```

JDK 位于 `%LOCALAPPDATA%\Programs\Microsoft\OpenJDK`，Android SDK 位于
`%LOCALAPPDATA%\Android\Sdk`。只有确认没有被其他项目使用时，才手工删除对应的精确目录，
不要递归删除整个 `%LOCALAPPDATA%\Android` 或用户目录。

### 2.4 iOS App 额外要求

iOS 自动化只能在 macOS 上运行，需要 Xcode、可用的模拟器或真机，并安装 XCUITest Driver：

```bash
appium driver install xcuitest
```

## 3. 第一次安装项目

### 3.1 获取代码并创建虚拟环境

```powershell
git clone <你的仓库地址>
cd web-api-app-autotest
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

激活成功后，命令行前面会出现 `(.venv)`。每次重新打开终端都要重新激活。

如果 PowerShell 不允许激活脚本：

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
.\.venv\Scripts\Activate.ps1
```

### 3.2 一次安装全部依赖

项目只有一个依赖文件：

```powershell
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m playwright install chromium
```

`requirements.txt` 已包含 API、Web、App、MySQL、Redis、Allure、pytest 和 Ruff。

### 3.3 创建本地敏感配置

```powershell
Copy-Item .env.example .env
```

`.env` 已被 `.gitignore` 排除，不要强制提交。

App 自动化至少需要填写：

```dotenv
APP_PATH=C:\path\to\your-app.apk
APPIUM_AVD=Pixel_6_API_34
APPIUM_UDID=
APPIUM_PLATFORM_VERSION=14
APPIUM_SERVER=http://127.0.0.1:4723
APPIUM_MANAGE_SERVER=true
```

- 模拟器保留 `APPIUM_AVD`，真机改填 `APPIUM_UDID`；两者不要同时填写。
- `APP_PATH` 放本机 APK 路径，不要把 APK 和绝对路径提交到 Git。
- `APPIUM_MANAGE_SERVER=true` 时框架自动启动/关闭本机 Server；已有 Server 只复用、不关闭。
- 新终端仍读不到 SDK/JDK 时，可在本地 `.env` 补充 `ANDROID_HOME` 和 `JAVA_HOME`。

### 3.4 第一次必须执行的检查

```powershell
python scripts/automation.py doctor --env uat
python scripts/automation.py doctor --env uat --type app
python scripts/automation.py self-test
```

- `doctor`：检查 Python、依赖、配置、Playwright、Appium、ADB、Java。
- `doctor --type app`：把 SDK、JDK、UiAutomator2、安装包和 AVD 作为阻断项检查。
- `self-test`：运行完全离线的框架自测，不访问业务系统。

## 4. 目录说明

```text
api/                 API 业务封装
pages/               Web Page Object
screens/             App Screen Object
testcases/api/       真实 API 用例
testcases/web/       真实 Web 用例
testcases/app/       真实 App 用例
tests/framework/     框架自身离线测试
fixtures/            登录态、数据准备、自动清理
clients/             MySQL、Redis、通知、邮件
core/                HTTP、断言、Web/App driver、安全保护
config/              多环境配置
data/                YAML、JSON、Excel、文本测试数据
utils/               日志、随机数据、日期、JSONPath 等工具
scripts/             统一命令和 CI 汇总脚本
reports/             运行生成的报告，不提交 Git
logs/                运行日志，不提交 Git
```

最重要的放置规则：

- 接口路径和请求细节放 `api/`。
- Web 定位器和页面行为放 `pages/`。
- App 定位器和页面行为放 `screens/`。
- `testcases/` 只写场景和断言。
- 多组数据放 `data/`。
- 通用前置和清理放 `fixtures/`。
- 账号、密码、token、webhook 只放 `.env` 或 CI Secret。

## 7. Marker 规则

| Marker | 用途 |
|---|---|
| `api` / `web` / `app` | 测试端类型 |
| `smoke` | 每次提交执行的核心链路 |
| `regression` | 定时完整回归 |
| `p0` / `p1` / `p2` | 业务优先级 |
| `prod_safe` | 人工审核后的生产只读用例 |
| `flaky` | 已登记的不稳定用例，不代表自动重试 |
| `timeout(秒)` | 覆盖单条用例的默认超时时间 |

每个真实用例至少标记端类型和优先级：

```python
@pytest.mark.api
@pytest.mark.smoke
@pytest.mark.p0
def test_create_order():
    ...
```

框架使用 `pytest-timeout` 防止请求、浏览器或设备异常后无限卡住：

| 用例类型 | 默认超时 |
|---|---:|
| API | 60 秒 |
| Web | 180 秒 |
| App | 300 秒 |
| 没有端类型标记 | 300 秒兜底 |

超时按“单条测试用例”计算，不是整批任务的总时长。确实需要更长时间时，只覆盖该用例：

```python
@pytest.mark.app
@pytest.mark.timeout(600)
def test_large_file_upgrade(app_driver):
    ...
```

不要为了绕过死锁而随意增大超时；先检查网络请求、显式等待、Appium Server 和设备状态。

## 8. API 自动化操作步骤

### 8.1 第一步：封装业务 API

假设接口是 `GET /api/products/{id}`，创建 `api/product_api.py`：

```python
"""商品模块 API 封装。"""

import allure

from api.base_api import BaseApi


class ProductApi(BaseApi):
    @allure.step("查询商品: id={product_id}")
    def get_product(self, product_id: int):
        return self.client.get(f"/api/products/{product_id}")

    @allure.step("创建商品")
    def create_product(self, payload: dict):
        return self.client.post("/api/products", json=payload)
```

不要在业务 API 类里写完整域名，环境地址由配置统一管理。

### 8.2 第二步：编写用例

创建 `testcases/api/test_product_api.py`：

```python
"""商品接口测试。"""

import allure
import pytest

from api.product_api import ProductApi
from core.assertions import Assert


@allure.feature("商品接口")
@pytest.mark.api
class TestProductApi:
    @pytest.mark.smoke
    @pytest.mark.p0
    def test_get_product_success(self, api_client):
        response = ProductApi(client=api_client).get_product(product_id=1001)

        Assert.status_code(response, 200)
        Assert.json_value(response, "code", 0)
        Assert.jsonpath(response, "$.data.id", 1001)
```

不要只断言 HTTP 200；还要断言业务 code、关键字段、状态和数据类型。

### 8.3 登录态复用

多个 API 模块共享同一个 `api_client`：

```python
def test_order_flow(api_client, env_settings):
    user_api = UserApi(client=api_client)
    order_api = OrderApi(client=api_client)

    user_api.login(env_settings.username, env_settings.password)
    response = order_api.create_order(product_id=1001, quantity=1)
    Assert.status_code(response, 200)
```

登录后 token/cookie 保存在同一个 Session 中。

### 8.4 数据驱动

`data/login_data.yaml`：

```yaml
- case_id: login_success
  username: valid_user
  password: correct_password
  expected_status: 200
- case_id: login_wrong_password
  username: valid_user
  password: wrong_password
  expected_status: 401
```

用例：

```python
login_cases = load_yaml("login_data.yaml")


@pytest.mark.parametrize("case", login_cases, ids=[case["case_id"] for case in login_cases])
def test_login(case, api_client):
    response = UserApi(client=api_client).login(case["username"], case["password"])
    Assert.status_code(response, case["expected_status"])
```

### 8.5 常用断言

```python
Assert.status_code(response, 200)
Assert.json_value(response, "code", 0)
Assert.jsonpath(response, "$.data.status", "PAID")
Assert.jsonpath_exists(response, "$.data.token")
Assert.contains(response.json(), "data")
Assert.equal(actual, expected)
Assert.not_empty(value)
Assert.approx(actual_amount, expected_amount, tol=0.01)
Assert.match_schema(response, schema)
```

### 8.6 数据库断言和自动清理

```python
def test_create_order(api_client, db, clean_data):
    response = OrderApi(client=api_client).create_order(product_id=1001, quantity=1)
    order_id = response.json()["data"]["order_id"]

    # 创建成功后立即登记清理，后续断言失败也会执行
    clean_data.add_table("orders", "order_id=%s", [order_id])

    row = db.query_one(
        "SELECT status, amount FROM orders WHERE order_id=%s",
        [order_id],
    )
    Assert.equal(row["status"], "CREATED")
```

SQL 必须参数化，不要拼接用户输入。生产环境 DB/Redis 写操作会被框架直接阻止。

### 8.7 API 用例设计清单

每个重要接口至少考虑：

- 正常参数。
- 必填参数缺失。
- 空值、0、负数、最大长度、超长值。
- 不存在的业务 ID。
- 无 token、过期 token、错误角色、越权访问。
- HTTP 状态码和业务 code。
- 关键响应字段和 JSON Schema。
- 写操作后的查询接口或数据库验证。
- 重复请求和幂等性。

## 9. Web 自动化操作步骤

### 9.1 配置浏览器

`config/config.yaml`：

```yaml
web:
  browser: chromium
  headless: true
  slow_mo: 0
  viewport:
    width: 1920
    height: 1080
  trace: true
```

本地调试使用 `--headed --slowmo 500`，CI 使用无头模式。

### 9.2 获取稳定定位器

优先级：

```text
data-testid / id / role > 稳定文本 > CSS class > XPath
```

建议推动开发为关键控件提供 `data-testid`。不要依赖动态 class、元素下标和超长 XPath。

Playwright 录制：

```powershell
python -m playwright codegen --target python https://你的系统地址
```

录制结果只用于获取操作步骤和定位器，最终要整理为 Page Object，不要把裸录制代码直接堆进用例。

### 9.3 创建 Page Object

`pages/login_page.py`：

```python
"""登录页面对象。"""

import allure

from pages.base_page import BasePage


class LoginPage(BasePage):
    URL = "/login"
    INPUT_USERNAME = "[data-testid='username']"
    INPUT_PASSWORD = "[data-testid='password']"
    BTN_LOGIN = "[data-testid='login-btn']"
    USER_AVATAR = "[data-testid='user-avatar']"

    @allure.step("执行登录: {username}")
    def login(self, username: str, password: str):
        self.open(self.URL)
        self.fill(self.INPUT_USERNAME, username)
        self.fill(self.INPUT_PASSWORD, password, sensitive=True)
        self.click(self.BTN_LOGIN)
```

密码、token、手机号等敏感输入使用 `sensitive=True`。框架也会根据定位器名称自动识别常见敏感字段。

### 9.4 创建 Web 用例

```python
"""Web 登录测试。"""

import allure
import pytest

from pages.login_page import LoginPage


@allure.feature("Web 登录")
@pytest.mark.web
class TestLoginWeb:
    @pytest.mark.smoke
    @pytest.mark.p0
    def test_login_success(self, page, env_settings):
        login_page = LoginPage(page)
        login_page.login(env_settings.username, env_settings.password)
        login_page.expect_visible(LoginPage.USER_AVATAR)
```

Playwright 自带等待。不要写固定 `sleep`，使用 `expect_*`、Locator 或明确的事件等待。

### 9.5 Web 用例控制数量

适合 Web 自动化：

- 登录和退出。
- 核心下单、支付前置、审批、发布等主链路。
- 关键页面展示和表单交互。
- 浏览器兼容性验证。

不适合大量放在 Web：

- 参数组合和边界值。
- 大量权限矩阵。
- 后端复杂状态流转。
- 可以通过 API 快速覆盖的业务分支。

### 9.6 BOSS 发票查询示例


已确认的 UAT 地址，SIT 和 PROD 仍是示例占位地址。生产环境仍受框架双重保护，

## 10. App 自动化操作步骤

### 10.1 启动设备和 Appium

首次使用先执行第 2.3 节的一键安装。日常执行不需要手工输入 `appium`：

```powershell
python scripts/automation.py doctor --env uat --type app
python scripts/automation.py app-smoke --env uat
```

`app-smoke` 的完整顺序是：读取 `.env` → 启动或复用 Appium Server → 启动或复用
`Pixel_6_API_34` → 安装 APK → 创建 Session → 输出 package/activity → 退出 Session →
只关闭本次自动启动的 Server。

看到下面两项就表示底层链路可用：

```text
[通过] Appium Session: <session-id>
[通过] 当前 package/activity: <package>/<activity>
```

需要观察模拟器界面时，可先手工启动：

```powershell
emulator -avd Pixel_6_API_34 -no-boot-anim -no-snapshot-save
adb devices -l
```

`adb devices -l` 出现 `emulator-5554 device` 后再运行用例。退出模拟器可在窗口中正常关闭，
不要直接删除 `.android\avd` 目录。

### 10.2 获取包名和 Activity

框架在 `app-smoke` 成功后会直接输出 package/activity。也可以在目标 App 位于前台时查询：

```powershell
adb shell dumpsys window | findstr mCurrentFocus
```

输出中 `/` 前面是 `appPackage`，后面是 `appActivity`。

### 10.3 配置 capabilities

`config/config.yaml`：

```yaml
app:
  appium_server: "http://127.0.0.1:4723"
  manage_server: true
  platform: "Android"
  android:
    platformName: "Android"
    automationName: "UiAutomator2"
    deviceName: "Android Emulator"
    avd: "Pixel_6_API_34"
    noReset: false
    autoGrantPermissions: true
    newCommandTimeout: 120
    adbExecTimeout: 60000
    avdLaunchTimeout: 120000
    avdReadyTimeout: 120000
```

不要用 `deviceName` 选择具体设备，它在 UiAutomator2 中主要是描述字段：

- 模拟器由 `avd` / `APPIUM_AVD` 选择。
- 真机由 `udid` / `APPIUM_UDID` 选择。
- APK 优先通过本地 `.env` 的 `APP_PATH` 配置。
- 已安装 App 也可使用 `APP_PACKAGE` + `APP_ACTIVITY`，但两项必须配套。
- 默认 `noReset: false` 保证用例隔离；确需保留登录态时才改为 `true`。

切换到公司 APK 时只修改本地 `.env`：

```dotenv
APP_PATH=D:\builds\company-app-uat.apk
APPIUM_AVD=Pixel_6_API_34
APPIUM_UDID=
APP_PACKAGE=
APP_ACTIVITY=
```

切换真机：

```powershell
adb devices -l
```

```dotenv
APPIUM_AVD=
APPIUM_UDID=你的设备序列号
```

设置 `APPIUM_UDID` 后，框架会自动忽略 YAML 中的 `avd`，避免模拟器与真机冲突。

### 10.4 使用 Appium Inspector 获取定位器

1. 启动设备和 Appium Server。
2. 打开 Appium Inspector。
3. 填入与 `config.yaml` 一致的 capabilities。
4. 创建 Session。
5. 点击控件，读取 `resource-id` 或 `content-desc`。

定位优先级：

```text
resource-id > accessibility id > Android UiAutomator > XPath
```

### 10.5 创建 Screen Object

```python
"""App 登录页面对象。"""

import allure

from screens.base_screen import BaseScreen


class LoginScreen(BaseScreen):
    INPUT_USERNAME = (BaseScreen.ID, "com.company.app:id/username")
    INPUT_PASSWORD = (BaseScreen.ID, "com.company.app:id/password")
    BTN_LOGIN = (BaseScreen.ID, "com.company.app:id/login")
    HOME_TAB = (BaseScreen.ACCESSIBILITY_ID, "home_tab")

    @allure.step("App 登录: {username}")
    def login(self, username: str, password: str):
        self.input(*self.INPUT_USERNAME, username)
        self.input(*self.INPUT_PASSWORD, password, sensitive=True)
        self.click(*self.BTN_LOGIN)

    def is_login_success(self) -> bool:
        return self.is_displayed(*self.HOME_TAB)
```

### 10.6 创建 App 用例

```python
"""App 登录测试。"""

import allure
import pytest

from screens.login_screen import LoginScreen


@allure.feature("App 登录")
@pytest.mark.app
class TestLoginApp:
    @pytest.mark.smoke
    @pytest.mark.p0
    def test_login_success(self, app_driver, env_settings):
        screen = LoginScreen(app_driver)
        screen.login(env_settings.username, env_settings.password)
        assert screen.is_login_success(), "登录后未进入首页"
```

不要为了“先绿起来”长期保留 `skip`。安装包、设备和定位器就绪后，至少提交一条真正执行的
App 冒烟用例；底层安装验证则使用 `app-smoke`，不要混入业务用例目录。

### 10.7 App 稳定性规则

- 不使用固定 `sleep`，使用显式等待。
- 优先稳定 ID，不使用坐标点击作为主要方案。
- 每条用例明确初始状态。
- 测试账号和测试数据相互隔离。
- 失败时查看截图、package、activity 和 Appium Server 日志。
- 自动管理的 Server 日志位于 `logs/appium-server.log`。
- App 测试成本高，先覆盖 3～5 条核心冒烟，再逐步增加。

## 11. 三端协作的推荐写法

同一个“下单”功能：

- API：覆盖正常、库存不足、优惠、权限、重复提交、状态流转。
- Web：只验证浏览器可以完成一次正常下单。
- App：只验证移动端可以完成一次正常下单以及必要的系统交互。

UI/App 的数据准备优先调用 API：

```text
API 创建测试用户和商品 -> Web/App 执行核心操作 -> API/DB 验证结果 -> API/DB 清理
```

但如果测试目标本身就是“页面创建订单”，不能用 API 替代这个被测步骤。

Web 流程背后的 API 序列可以通过 `network_recorder` fixture 捕获：

```python
def test_capture_flow(page, network_recorder):
    LoginPage(page).login("user", "password")
    # 继续执行核心 UI 流程
    network_recorder.print_summary()
    network_recorder.save("captured_apis.json")
```

录制内容会经过脱敏，但仍应把输出当成测试内部资料，不提交真实业务数据。

## 13. 报告、日志和失败排查

默认结果目录：

```text
reports/runs/<UTC时间-随机运行编号>
```

每次启动都会打印本次 Allure 目录，不会自动清理前一次三端结果。查看最近一次报告：

```powershell
python scripts/automation.py report
```

失败时框架会尽量收集：

- Web/App 截图。
- Web 当前 URL 和标题。
- App 当前 package 和 activity。
- API 请求、响应、状态码和耗时。
- Playwright Trace（配置开启时）。

日志保存在 `logs/`。HTTP 和断言按字段名进行脱敏，输入方法不自动向 Allure 记录原始参数。
无字段名的密码/token 标量用 `Assert.equal(actual, expected, sensitive=True)`。
这不是通用保密保证：截图、Trace、业务自行打印内容、异常和自定义步骤仍可能含敏感数据；分享前必须检查。

并行 pytest 进程不能同时对同一个 Allure 目录使用 `--clean-alluredir`。CI 必须使用独立目录：

```text

reports/allure-api
reports/allure-web
reports/allure-app
```

## 14. 生产环境安全规则

普通生产命令会直接终止：

```powershell
python scripts/automation.py test --type api --env prod
```

确实需要生产只读验证时，必须同时满足：

1. 用例经过人工审核并标记 `prod_safe`。
2. 命令带 `--allow-prod`。
3. 环境变量严格等于 `ALLOW_PROD_TESTS=1`。

```powershell
$env:ALLOW_PROD_TESTS="1"
python scripts/automation.py test --type api --env prod --allow-prod
Remove-Item Env:ALLOW_PROD_TESTS
```

即使授权成功：

- 只收集 `prod_safe` 用例。
- HTTP 只允许 GET、HEAD、OPTIONS。
- HTTP 只允许访问配置中的同源 API。
- DB 和 Redis 写操作会被阻止。
- 不允许使用创建数据和自动清理 fixture。

生产数据库账号仍应由 DBA 设置为只读，不要只依赖代码保护。

## 16. CI 接入

仓库提供：

- `.github/workflows/automation-test.yml`
- `.gitlab-ci.yml`
- `Jenkinsfile`

统一流程：

```text
安装 requirements.txt
  -> Ruff
  -> 框架 self-test
  -> API/Web 冒烟或回归
  -> 合并 Allure
  -> 钉钉/企微/邮件通知
```

### 16.1 CI Secret

根据实际使用配置：

```text
TEST_USERNAME / TEST_PASSWORD / API_TOKEN
DB_USER / DB_PASSWORD / REDIS_PASSWORD
DINGTALK_WEBHOOK / DINGTALK_SECRET
WECOM_WEBHOOK
SMTP_HOST / SMTP_PORT / SMTP_USER / SMTP_PASSWORD / EMAIL_TO
REPORT_URL
```

不要把真实值写进仓库。

### 16.2 GitHub Actions

1. 在仓库 Settings -> Secrets and variables -> Actions 配置 Secret。
2. 当前 push/PR 触发分支包含 `main` 和 `release`。定时任务仍由 GitHub 默认分支上的 workflow 决定。
3. 先在本地跑通真实业务，再在 Variables 设置 `ENABLE_API_TESTS=true` 和/或 `ENABLE_WEB_TESTS=true`。
   未开启的业务任务会明确 skipped；框架自测绿色不代表这些业务已验证。PR 仅运行离线自测，不带凭据访问业务。
4. BOSS Web 在本地用 `capture_boss_auth.py` 保存登录态，将对应 JSON 文件内容作为 Secret `BOSS_STORAGE_STATE_JSON`。
   CI 只在内存使用，不写入仓库。登录态过期后需重新捕获并更新 Secret；不要贴到日志或公开 Issue。
5. 报告默认作为 `business-allure-report` Artifact 保留 7 天。业务汇总排除框架自测；通知链接指向本次 Actions。
   仅在确认截图/附件可公开后，设置 Variable `PUBLISH_ALLURE_PAGES=true` 并启用 Pages。
6. Runner 无法访问内网环境时，给业务 job 使用可信的 self-hosted runner；不要把内网地址改成生产地址凑通过。
7. 启用后的任务没有用例、登录态缺失或全部 skip 均为失败。夜间选择 `smoke or regression`。

### 16.3 GitLab CI

1. Settings -> CI/CD -> Variables 配置 masked 变量。
2. 创建 Pipeline Schedule 执行每日 regression。
3. 内网环境使用公司 Runner。
4. GitLab Pages 不可用时把报告上传到内网服务器。

### 16.4 Jenkins

1. 安装 JUnit 和 Allure 插件。
2. 配置 Jenkinsfile 使用的凭据 ID。
3. Agent 安装 Python、Playwright 浏览器。
4. 每次提交运行 smoke，定时任务运行 regression。

### 16.5 App CI 特别说明

GitHub CI 默认只运行离线框架检查，API/Web 经上述开关启用。App CI 需要公司提供以下其中一种能力后再接入：

- 自托管 Runner + 固定真机。
- 自托管 Runner + Android 模拟器。
- 云真机平台。

App CI 还需要安装包来源、设备锁、Appium Server 生命周期和独立 Allure 目录。没有设备基础设施时，不要配置一个表面存在但无法稳定执行的 App job。

## 19. 常见问题

### 19.1 `ModuleNotFoundError`

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

### 19.2 Playwright 提示浏览器不存在

```powershell
python -m playwright install chromium
```

### 19.3 没有收集到业务用例

检查：

- 文件是否放在 `testcases/api|web|app`。
- 文件名是否以 `test_` 开头。
- 测试函数是否以 `test_` 开头。
- 是否添加了正确的 `api/web/app` marker。
- `--marker` 表达式是否把所有用例过滤掉。

模板初始化阶段才可使用 `--allow-empty`。

### 19.4 API 401/403

- 检查账号、token、角色。
- 检查是否使用同一个 `api_client` 保持登录态。
- 查看 Allure 中经过脱敏的请求头和响应。

### 19.5 Web 找不到元素

- 用 Playwright Inspector/codegen 重新确认定位器。
- 优先改为 `data-testid`、id 或 role。
- 等待业务状态，不使用固定 sleep。
- 查看失败截图和 Trace。

### 19.6 App 无法创建 Session

依次检查：

```powershell
adb devices
appium driver list --installed
python scripts/automation.py doctor --env uat --type app
```

然后确认：

- 是否先执行 `. .\scripts\use_android_env.ps1`，以及 `ANDROID_HOME`、`JAVA_HOME` 是否指向有效目录。
- 模拟器是否使用正确的 `APPIUM_AVD`，真机是否使用正确的 `APPIUM_UDID`。
- `APP_PATH` 文件是否存在，或 `APP_PACKAGE`/`APP_ACTIVITY` 是否配套。
- `logs/appium-server.log` 中第一条实际异常是什么。

如果日志出现 `Cannot find package '@appium/logger'`，这是部分 Windows/npm 组合安装
UiAutomator2 时可能出现的依赖问题。新版安装脚本会在 doctor 失败时停止，不再静默修改全局依赖。
确认实际错误和团队版本策略后，才考虑以下针对性修复，并重新运行 doctor：

```powershell
npm install --prefix "$env:USERPROFILE\.appium" --save-dev "@appium/logger@2.0.7"
appium driver doctor uiautomator2
```

`bundletool`、FFmpeg、GStreamer 属于 AAB、录屏或串流的可选能力；普通 APK UI 自动化
不应因为这些可选检查缺失而停止。

### 19.7 Allure 清理报错或结果丢失

默认结果目录已按运行隔离。若显式设置 `--alluredir`，请自行保证不同任务不共用目录；
不要让两个进程同时使用同一目录并开启 `--clean-alluredir`。显式目录重复运行默认累积结果。

### 19.8 用例偶发失败

先判断原因：

- 定位器不稳定。
- 测试数据冲突。
- 服务异步未完成。
- 环境网络波动。
- 用例之间有顺序依赖。

修复根因，不要直接增加全局重试。

## 21. 本轮稳定性优化后的操作方式（2026-09-07）

### 21.1 先验证框架，再接真实业务

```powershell
.\.venv\Scripts\Activate.ps1
python -m ruff format --check .
python -m ruff check .
python scripts/automation.py self-test
```

没有 Python 命令时先安装 Python 3.10–3.12，或使用已安装的 uv：

```powershell
uv venv --python 3.12 .venv
uv pip install --python .venv\Scripts\python.exe -r requirements.txt
.\.venv\Scripts\Activate.ps1
```

业务验收应分别执行三端命令，确保每一端确实有用例运行：

```powershell
python scripts/automation.py test --type api --env uat --marker smoke
python scripts/automation.py test --type web --env uat --marker smoke --headed
. .\scripts\use_android_env.ps1
python scripts/automation.py doctor --env uat --type app
python scripts/automation.py app-smoke --env uat
python scripts/automation.py test --type app --env uat --marker smoke
```

`app-smoke` 仅验证 Session，不证明登录、提交、查询等业务正确；它可能安装或重置 App，
因此即使有生产只读授权也不允许在 prod 执行。当前 API/App 业务目录没有真实用例时，
对应 test 命令失败是正确行为，不要添加永远通过的占位测试。

统一 `test` 入口自动开启 `--require-executed`；直接调用 pytest 时需自己加这个开关：

```powershell
python -m pytest testcases/web -m web --env uat --require-executed
```

`--type all` 表示一次收集全部现有用例，不保证每个端都有覆盖；上线验收仍应分端执行。
只有 xfail/skip 而没有实际通过/失败结果，也不会被业务门禁认作验证完成。

### 21.2 身份与数据隔离

- `HttpClient()` 或 `token=None` 沿用 `.env` 中的 `API_TOKEN`。
- `HttpClient(token="")` 清除客户端继承的 Authorization、Session auth 和 Cookie；匿名测试优先用 `anonymous_client`。
- 多角色使用各自的客户端，不在共享 Session 上来回调用 `set_token`。
- `logged_in_client` 改为 function 级，每条用例重新登录并独立关闭；不要再从 session/module 级 fixture 引用它。
- 当前登录适配器仍按 `/api/login` 和顶层非空字符串 `token` 校验；新公司若有业务码、嵌套 token 或 SSO，必须按真实协议调整，不是改账号就能通用。
- 数据准备继续使用已有 `clean_data`、`unique_id`、`wait_until`。清理回调内应断言删除响应成功；不要只调用接口就当清理完成。

### 21.3 App 环境的可恢复性

新版脚本固定 JDK 下载地址及 SHA-256；坏缓存会重命名为 `.invalid.<随机编号>` 保留，重新下载。
外部命令非零退出码会阻断，不能把最后一行提示当作真实 Appium 连接验收。
安装脚本本轮只做语法和安全逻辑验证，仍需在干净 Windows 机器验证完整下载/安装流程。

每个新终端启用工具链；非默认目录显式指定：

```powershell
. .\scripts\use_android_env.ps1 -SdkRoot "D:\Android\Sdk" -JdkHome "D:\Java\jdk21"
```

关闭该终端即可撤销此次进程环境切换。旧版脚本已经修改过的用户环境变量不会被新版自动还原，
避免覆盖你后来做的调整；需要时通过 Windows 环境变量设置，根据原有值手工恢复。
安装的 SDK/JDK/AVD 仍留在磁盘；Git 回滚不会卸载工具、恢复环境变量或删除 `.venv`。

## 22. 入口与诊断补充优化（2026-09-11）

### 22.1 报告入口

```powershell
# 自动选择 reports/runs 中最近一个包含 *-result.json 的目录
python scripts/automation.py report

# 检查特定一次运行，或查看 CI 下载的原始结果目录
python scripts/automation.py report --path "D:\test-results\allure-api"
```

`make report` 使用同一入口。空目录、只有附件的目录不会被自动选中；没有结果或未安装
Allure 命令行会返回失败并提示。不会删除旧报告，也不会自动退回历史遗留的 allure-results。
“最近一次”可能是框架自测，不一定是业务；验收时请核对运行输出的目录，必要时传 `--path`。

### 22.2 分端 doctor

```powershell
python scripts/automation.py doctor --env uat --type api
python scripts/automation.py doctor --env uat --type web
python scripts/automation.py doctor --env uat --type app
```

- 不指定 `--type`：基础诊断及可选工具提示，不代表三端已验收。
- API：检查核心依赖和配置，不发送业务请求、不验证账号或数据库连通性。
- Web：额外要求 Playwright/pytest-playwright，启动配置中的无头浏览器后关闭，只开空白页、不访问业务。
- App：额外要求 Appium Python Client/Selenium，再执行现有本机驱动、JDK、SDK 和设备检查。
- 缺少核心依赖时，doctor 在加载配置前返回失败，仍可提示安装 requirements.txt。
- App doctor 当前仍是本机工具链检查；使用远程设备服务时，需另外在服务端验收环境。

### 22.3 并行与启动前检查

`make parallel` 只收集 `testcases/api` 和 `testcases/web`，排除 app 标记，并开启
`--require-executed`；App 仍保持单设备串行。调用前应先准备隔离的数据和账号。

App 原生测试在启动托管 Server、创建 Session 前检查目标配置：
本机安装包路径必须存在；不安装新包时，Android 必须有包名和启动页，iOS 必须有 bundleId。
远程 Server 的文件路径属于服务端，不能在客户端判断是否存在，仍由服务端校验。
`appium_server_ready` 对错误 JSON、空字段、非法 URL 返回未就绪，不再因这些响应直接崩溃。

### 22.4 无效配置和流水线超时

删除了未生效的 `common.retry` / `settings.retry`。需要等待异步结果时继续使用 `wait_until`；
特定幂等操作的重试应在调用点显式配置，不重新引入全局失败重跑。

GitHub：框架 30 分钟、API/Web 各 45 分钟、报告 15 分钟、通知 10 分钟。
GitLab 对应任务使用相同上限；Jenkins 流水线总上限为 60 分钟。实际业务规模增大后再调整。
这些是运行兜底，不保证强制超时后所有 teardown、报告生成或外部进程清理都能完成。

本轮基线保留在 `codex/backup-before-entry-polish-20260911`，优化单独提交；
需要回滚时先保存未提交工作，再对本轮提交执行 `git revert`，不要整目录覆盖。
